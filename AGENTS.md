# Инструкции и стандарты разработки для ИИ-агентов (AGENTS.md)

Данный документ определяет обязательные правила, архитектурные инварианты и стандарты качества для любых ИИ-агентов и разработчиков, работающих с репозиторием.

## 0. Общие принципы и язык

1. **Русский язык**: 
Всё общение в чате, рассуждения, проектная документация, комментарии и описания коммитов ведутся на русском языке.
2. **Итеративность**: 
Работа ведётся небольшими проверяемыми шагами. Запрещено накапливать крупные нетестированные изменения.
3. **Архитектурное согласование**: 
Любые архитектурные предложения, спорные моменты и интерпретации требований сначала обсуждаются с пользователем и только после подтверждения реализуются в коде.
4. **Принцип экономии токенов**: 
Избегать избыточной бюрократии, длинных монологов и генерации промежуточных служебных файлов, если решение уже согласовано в диалоге.
5. **Простота решений**: 
Выбирать самое простое решение, которое полностью выполняет требования. Не добавлять абстракции, зависимости и функциональность «на будущее». Необходимые усложнения сначала объяснять и согласовывать с пользователем.
7. **Рабочая среда**: 
Работать в текущей ветке. Не создавать другие ветки или worktree и не выполнять push без указания пользователя.

## 1. Соглашения по коммитам (Semantic Git Commits)

Формат коммита:
```
<TYPE>: <описание изменений на русском языке>
```

### Разрешенные префиксы (на английском языке):

- `ADD:` — добавление новой функциональности, файлов, тестов, страниц или маршрутов.
- `UPD:` — обновление существующей логики, стилей, шаблонов, рефакторинг без смены назначения.
- `FIX:` — исправление багов, опечаток, ошибок в коде или стилях.
- `RM:` — удаление устаревших файлов, зависимостей или неиспользуемого кода.
- `DOC:` — обновление или создание документации (`ARCHITECTURE.md`, `AGENTS.md`, спецификации).
- `TEST:` — добавление или модификация тестов (`test-e2e.js`).
- `REFACTOR:` — структурная переработка кода без изменения внешней функциональности.

### Примеры:

- `ADD: добавление маршрута API для управления статьями`
- `UPD: оптимизация сетки карточек в catalog.css`
- `FIX: корректная обработка сессионной cookie при выходе из админки`
- `DOC: добавление ARCHITECTURE.md и AGENTS.md`

### Порядок выполнения команды `git commit ...`:

Агенту **категорически запрещено** выполнять `git commit` автоматически.

Перед каждым коммитом агент обязан:

1. Сразу после окончания работы сформулировать и вывести пользователю **краткую сводку ревью** (без списков файлов, дублирования задач и логов):
- **Суть изменений**: буквально 1–3 предложения простыми словами о том, что было сделано.
- **Предлагаемый текст коммита**: строго по формату раздела 1.
- **Ручные проверки**: указывать только при реальной необходимости (шаги ручной проверки, оценка UI, спорные вопросы). Если ручная проверка не требуется, пункт опускается.
2. **Остановиться** и дождаться явного подтверждения предложенного коммита («коммить», «ок» или замечания). Если пользователь подтвердил коммит без замечаний, дополнительное согласование не требуется.
3. После подтверждения один раз выполнить необходимые для изменения проверки в тихом режиме (без вывода в чат при успехе) и только если они требуются. Делать проверки ради проверок не нужно. После этого создать коммит. Если нужные проверки уже прошли и после них изменения не вносились, проверки не повторять. При ошибках исправить причину и повторить только затронутые проверки.

## 2. Правила работы с инструментами (Tool Hygiene)

1. **Хирургическая точечность изменений**:
- Для обычного редактирования файлов по возможности использовать инструмент точечных изменений с компактными блоками замены и видимым пользователю diff (например, `apply_patch` или `replace_file_content`).
- Python, shell и другие скрипты допустимы только для массовых однотипных замен и преобразований, когда это проще точечных правок. Дополнительное объяснение и дублирование diff в чате не требуются.
- Не перезаписывать весь файл целиком (`write_to_file` с `Overwrite: true`), если нужно изменить только часть строк.

2. **Сохранение целостности документации**:
- Не удалять комментарии, JSDoc и пояснения в коде при проведении рефакторинга.

3. **Минимизация вывода команд (Zero-Defect)**:
- Обычные автоматические проверки (форматирование, сборка, тесты) выполнять один раз перед созданием коммита, после подтверждения пользователя, в объёме, соответствующем изменению. Для изменений только документации сборка и тесты приложения не нужны.
- Во время реализации запускать только точечные проверки, необходимые для выяснения ошибки или проверки поведения. Уже успешную проверку повторять только после изменений, влияющих на её результат, или при появлении новой проблемы.
- Вызовы команд верификации, тестов и сборки обязаны быть максимально лаконичными: ровно 1 строка статуса при успехе, вывод только ошибок при сбоях.
- Категорически запрещено засорять контекст подробными логами успешных проверок.

4. **Переносимость**:
- Использовать доступные инструменты агента; правила проекта не зависят от названий конкретных инструментов редактирования.
